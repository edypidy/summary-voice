# Phase 0 결과 — 불합격 (2026-07-29)

README 섹션 4의 게이트를 실제로 통과시켜 봤다. **음성 낭독 UX는 불합격이다.**
전송 계층은 합격이다. 이 둘을 구분하는 것이 이 문서의 요점이다.

## 무엇을 쟀나

`sv-send --ruler`로 80~500자 메시지 9개를 20초 간격으로 텔레그램에 보내고,
안드로이드에서 이어폰으로 들었다. 총 4회 실행.

## 결과

| 항목 | 결과 |
|---|---|
| 텔레그램 전송 | **합격.** 지연 없이 도착 |
| 안드로이드 알림 낭독 | **합격.** 별도 앱 설치로 메시지 도착 즉시 낭독됨 |
| 낭독 UX 전반 | **불합격.** 사용자 평: "생각보다 사용성이 안 좋다" |
| 낭독 최대 글자 수 | **측정 안 함.** 위 판정으로 측정할 이유가 사라졌다 |

## 판정

> "그냥 메신저로 전달받고, 지시사항 전달하는 정도가 나은 것 같네.
> 음성 관련된건 제일 마지막 스텝으로 만드는게 나아보여" — 사용자, 2026-07-29

기술 경로가 막힌 게 아니다. **경로는 다 뚫렸는데 그 위의 경험이 원하는 게 아니었다.**
텔레그램도 되고 TTS도 됐다. 듣는 것 자체가 읽는 것보다 나을 게 없었다.

Gemini 낭독 앱 목록에 텔레그램이 있는지는 끝내 확인 못 했다. 사용자가 서드파티
낭독 앱을 따로 설치해 우회했고, 그 뒤로는 이 질문이 무의미해졌다.

## 이 결과가 바꾼 것

Phase 0을 맨 앞에 둔 이유가 정확히 이거였다 (README 섹션 4). 파이프라인을 다 만든
뒤에 이 판정이 나왔으면 **내레이션 생성기·용어집·STT 교정이 통째로 버려졌을 것이다.**
지금은 아직 안 만든 것이 버려졌다.

바뀐 것:

1. **음성이 범위에서 빠졌다.** TTS, STT, 용어집, term recall 평가 전부.
   프로젝트가 "듣는 것"에서 "읽는 것"으로 재정의됐다.

2. **내레이션 제약의 근거가 사라졌다.** 기존 제약 - 3문장 이하, 200자,
   "코드 블록·경로·긴 식별자 금지", "숫자 최소화" - 은 전부 **낭독 때문에**
   있던 것이다. 눈으로 읽는다면 `train.py:142`나 loss 값은 금지 대상이 아니라
   **있어야 유용한 정보**다. 섹션 6.3을 통째로 다시 썼다.

3. **양방향이 부차 목표에서 실질 목표로 올라왔다.** 사용자가 원하는 건 관측만이
   아니라 "지시사항 전달"이다. 다만 받기가 쓸모 있는지부터 확인한다 - 받기가
   시시하면 답장할 일도 없다.

## 되살릴 때 필요한 것

음성 코드는 지웠지만 git 히스토리에 있다. 커밋 `5c58d8d` 시점의 트리에
용어집 추출기(`glossary/`), STT 2중 레이어 교정(`stt/`), term recall 평가,
낭독 자 수 측정기(`sinks/ruler.py`), 평가용 발화 20개(`data/`)가 전부 살아 있다.

```bash
git show 5c58d8d --stat
git checkout 5c58d8d -- src/summary_voice/glossary src/summary_voice/stt
```

되살릴 거라면 이 문서의 판정부터 다시 읽을 것. 문제는 코드 품질이 아니라
**듣기가 읽기보다 나을 게 없었다**는 것이었다. 코드를 되살려도 그건 안 바뀐다.
