# 음성 연구 비서 PoC — 구현 플랜

> **이 문서를 받는 구현자에게**: 이 문서는 자기완결적입니다. 이전 대화 맥락이 없어도 구현 가능하도록 작성되었습니다. 명시되지 않은 부분은 "열린 질문" 섹션을 확인하고, 임의로 결정했다면 결정 사항을 기록하세요.

---

## 1. 문제 정의

연구자가 Claude Code 에이전트에게 연구 작업을 위임해 두고 자리를 비웠을 때, **현재 무엇이 진행되고 있는지를 이어폰으로 들을 수 있어야 한다.** 지금은 터미널로 돌아가 코드를 직접 읽거나 에이전트에게 물어봐야만 파악이 된다.

부차적으로, 들은 내용에 대해 음성으로 되묻거나 지시할 수 있으면 좋다. **단, 이는 PoC 범위가 아니다.**

### 사용자 프로파일 (중요)
- 주 사용 언어: **한국어**. 단, 전문 용어는 영어를 그대로 섞어 씀 (code-switching).
- 도메인: 의료영상 AI 연구. 등장 용어 예시 — `LoRA-XS`, `Sinkhorn`, `Mutual EM Attention`, `STE hard selection`, `cross-attention`, `PEFT`, 그리고 레포 고유 식별자(`hierarchical_cross_attention.py` 등).
- **이 code-switching 조합이 이 프로젝트의 최대 기술 리스크다.** (섹션 7 참조)

## 2. 범위

### PoC에 포함
- Claude Code 세션에서 이벤트 수집
- 이벤트 → 짧은 한국어 내레이션 요약
- Slack으로 푸시 (프로젝트당 채널 1개)
- 이어폰 낭독 UX 검증
- 프로젝트별 전문 용어집 자동 생성
- 음성 입력의 전문 용어 인식 정확도 측정 및 교정 파이프라인

### PoC에서 제외 (v2로 미룸)
- 살아있는 세션에 명령을 주입하는 Injector (양방향 제어)
- 실시간(토큰 단위) 스트리밍 내레이션 — 마일스톤 단위로 충분
- 멀티 호스트, 인증, 다중 사용자
- 자체 모바일 앱 — OS 기본 기능으로 대체

## 3. 아키텍처

```
[Host: 연구 머신]
  Claude Code Agent 1 ─┐
  Claude Code Agent 2 ─┼─(Hooks)─→ 큐 디렉터리 ─→ events.jsonl (append-only)
  ...                  ┘                              │
                                                      ▼
                                          Relay Daemon (별도 프로세스)
                                          - 디바운스 / 살리언스 판정
                                          - state.json 갱신
                                          - 요약 LLM 호출
                                                      │
                                                      ▼
                                       Slack #proj-<name> 채널
                                                      │
[Device: 폰 + 이어폰]                                  ▼
                                       OS 알림 자동 낭독 (TtoS)
                                       음성 답장 → STT → 용어 교정
```

### 핵심 설계 원칙 (위반 금지)

1. **관측과 제어는 별개 경로다.** Claude Code 세션은 서버가 아니므로 쿼리할 수 없다. 읽기는 훅이 밀어내는 push 방식뿐이다. PoC는 읽기만 구현한다.
2. **훅은 논블로킹이어야 한다.** 훅은 에이전트 루프의 크리티컬 패스에서 동기 실행된다. 훅 안에서 LLM 호출·TTS·네트워크 I/O를 하면 연구 세션 자체가 느려진다. 훅은 **JSON 한 줄을 큐에 쓰고 즉시 exit 0** 한다. 그 이상은 하지 않는다.
3. **Relay는 stateless여야 한다.** 모든 상태는 디스크에 있다. Relay가 죽었다 살아나도 events.jsonl부터 재구성 가능해야 한다.
4. **Relay는 Claude Code 에이전트가 아니라 단순 API 호출이다.** 요약기에 툴이나 파일시스템 접근 권한을 주지 않는다. 프로젝트마다 상주 에이전트를 띄우면 토큰 비용이 폭발한다.
5. **내레이션은 알림 한 개 분량을 넘지 않는다.** 섹션 6.3의 제약을 반드시 지킬 것.

## 5. 이벤트 수집

### 5.1 훅 설정

Claude Code Hooks를 사용한다. **구현 전에 반드시 최신 문서로 스키마를 확인할 것** — 훅 스펙은 자주 바뀐다.
- https://code.claude.com/docs/en/hooks
- Agent SDK로 감쌀 경우: https://platform.claude.com/docs/en/agent-sdk/hooks

사용할 이벤트:

| 이벤트 | 용도 | 비고 |
|---|---|---|
| `Stop` | **주 트리거.** 턴/작업 종료 = 마일스톤 | `session_id`, `transcript_path`, `cwd` 등을 전달받음. `transcript_path`가 요약 소스로 가장 유용 |
| `SubagentStop` | 서브에이전트 단위 완료 | 매처로 에이전트 타입 구분 가능 |
| `PostToolUse` | 보조 신호(어떤 파일/명령을 건드렸는지) | **관찰 전용.** 실행을 되돌리지 못함. 노이즈가 많으므로 필터 필수 |

주의사항:
- **매처는 대소문자를 구분한다.** `bash`는 `Bash`에 매칭되지 않는다.
- 훅 종류는 command / http / prompt 등이 있다. PoC는 **command 훅**을 쓴다 (디버깅이 쉽다).
- `exit 2`는 블로킹 의미를 가진다. 우리 훅은 **항상 exit 0** 해야 한다. 실수로 2를 반환하면 에이전트 동작에 개입하게 된다.
- 훅 등록 확인은 `/hooks`로, 테스트는 샘플 JSON을 stdin으로 파이프해서 종료 코드를 확인한다.

### 5.2 훅 스크립트 요구사항

```
stdin JSON 읽기
→ {ts, project, session_id, agent_id, event_type, payload} 로 정규화
→ <queue_dir>/<uuid>.json 으로 원자적 쓰기 (임시파일 write 후 rename)
→ exit 0
```

- 실행 시간 목표: **50ms 미만**. 네트워크 호출 금지.
- 어떤 예외가 나도 exit 0. 관측 레이어가 연구를 망가뜨리면 안 된다.
- `agent_id`를 반드시 넣을 것. 여러 에이전트가 동시에 돌 때 내레이션에서 구분해야 한다.

### 5.3 저장소 레이아웃

```
<project>/.assistant/
  queue/            # 훅이 쓰는 곳, Relay가 소비 후 삭제
  events.jsonl      # append-only, 원본 진실
  state.json        # events에서 파생된 현재 상태 (언제든 재생성 가능)
  glossary.json     # 섹션 7.1
  narrations.jsonl  # 발송 이력 (중복 방지 + 평가용)
```

`state.json` 스키마:
```json
{
  "goal": "현재 진행 중인 상위 목표 (사람이 이해하는 단위)",
  "in_progress": ["..."],
  "recently_done": ["..."],
  "blockers": ["..."],
  "last_narration_ts": "...",
  "last_event_offset": 0
}
```
`last_event_offset`으로 Relay 재시작 시 이어받는다.

## 6. Relay Daemon

### 6.1 루프

```
큐 폴링 (또는 파일시스템 watch)
→ 디바운스: 마지막 이벤트 후 N초 정적일 때만 발화 (기본 N=30, 설정 가능)
→ 살리언스 판정 (6.2)
→ 발화할 가치가 있으면: state.json + 신규 이벤트 델타 → LLM → 내레이션
→ state.json 갱신, narrations.jsonl 기록, Slack 전송
```

- 요약 모델: **Haiku 급**. 전체 트랜스크립트를 매번 넣지 말 것 — append-only라 금방 커진다. **state.json + 델타**만 넣는다.
- 프로젝트당 독립 워커. 프로젝트 간 상태를 섞지 않는다.

### 6.2 살리언스 — 이 PoC의 지적 핵심

가장 어려운 부분이자 결과물의 질을 좌우하는 부분이다. 목표는 **스팸도 아니고 중요한 걸 놓치지도 않는** 케이던스.

발화해야 하는 것:
- 마일스톤 완료 ("Sinkhorn OT 루프 구현 끝")
- 막힘/실패 (loss NaN, 테스트 실패, 반복되는 에러)
- 사람의 결정이 필요한 지점
- 방향 전환

발화하면 안 되는 것:
- 개별 파일 읽기/쓰기, `ls`, `grep`
- 진행 중인 중간 상태
- 직전 내레이션과 실질적으로 같은 내용

구현: 규칙 기반 1차 필터(이벤트 타입/툴 이름) → LLM 2차 판정(발화 여부를 boolean으로 먼저 물어보고, true일 때만 내레이션 생성). 2단계로 나누면 비용이 크게 준다.

### 6.3 내레이션 제약 (하드 제약)

- **한국어**, 3문장 이하, Phase 0에서 실측한 글자 수 이하 (미실측 시 잠정 200자)
- 코드 블록·경로·긴 식별자 금지 — **귀로 듣는 텍스트**다
- 파일명은 읽기 좋게: `hierarchical_cross_attention.py` → "크로스 어텐션 모듈"
- 숫자는 최소화. loss 값 나열 금지
- 에이전트가 여럿이면 주어를 명시 ("2번 에이전트가...")

**낭독 적합성이 텍스트 품질보다 우선한다.** 읽어서 좋은 요약과 들어서 좋은 요약은 다르다.

### 6.4 Slack

- **프로젝트당 채널 1개** (`#proj-<name>`). 이렇게 하면 라우팅 문제가 사라진다.
- Bot token + `chat.postMessage`면 충분하다.
- 알림 낭독이 동작하도록 알림 설정을 확인할 것 (Phase 0에서 검증됨).

## 7. 전문 용어 처리

### 7.1 용어집 자동 생성 (손으로 쓰지 말 것)

프로젝트별 `glossary.json`을 레포에서 자동 추출한다:

| 소스 | 추출 대상 |
|---|---|
| Python AST | 클래스명, 함수명, 모듈명 |
| config (yaml/json/argparse) | 키 이름 |
| `.tex` / 논문 초고 | 수식 심볼, 메서드명, 반복 등장하는 명사구 |
| git log | 커밋 메시지의 고유 명사 |
| README / CLAUDE.md | 프로젝트 고유 약어 |

각 항목에 표기 변형을 함께 저장한다: `{"canonical": "LoRA-XS", "variants": ["로라 XS", "lora xs", "LoRA XS"]}`

**용어집은 프로젝트별로 스코프한다.** 전역 용어집은 만들지 않는다. 프로젝트당 100개 이하로 유지되어 대부분의 API 제한 안에 들어가고, 정확도도 더 높다.

### 7.2 STT 파이프라인 (2중 레이어)

```
오디오 → [레이어 1: 디코딩 시점 바이어싱] → 원시 전사
      → [레이어 2: 용어집 기반 LLM 교정] → 최종 텍스트
```

**레이어 1 옵션** (하나 고를 것, 구현 전 최신 스펙 확인):
- self-host: `faster-whisper`의 `hotwords` 파라미터. Whisper의 `initial_prompt`는 길이 제한(~224토큰)이 강해 큰 용어집엔 부적합.
- 매니지드: Deepgram Keyterm Prompting (Nova-3, 추론 시점에 최대 100개, 재학습 불필요) / AssemblyAI Universal-3 (keyterm 최대 1,500단어) / Google PhraseSet + boost.
- Azure Custom Speech는 어휘 변경마다 재학습·재배포가 필요해 이 용도에 부적합.

**레이어 2** (이쪽이 실질적 주력일 가능성이 높다):
전사 결과 + 프로젝트 용어집을 작은 모델에 넘겨 오인식 용어만 교정. 프롬프트 요지: "아래는 한국어에 영어 전문용어가 섞인 발화의 전사문이다. 용어집을 참고해 오인식된 전문용어만 교정하고, 나머지 문장은 그대로 두라."

**왜 2중인가**: 대부분의 바이어싱 기능은 영어 기준으로 튜닝·검증되어 있다. "LoRA-XS 로스가 발산해요" 같은 한국어-영어 혼합 발화에서는 레이어 1만으로 부족할 가능성이 크다. Relay가 이미 붙어 있으므로 레이어 2는 사실상 공짜다.

### 7.3 평가 (필수 — 건너뛰지 말 것)

리더보드나 벤더 벤치마크를 믿지 말고 직접 잰다.

- 사용자가 실제로 할 법한 발화 **20개를 직접 녹음**한다. 반드시 한국어 문장 안에 영어 전문용어가 섞인 형태로.
- 지표는 전체 WER이 아니라 **용어 재현율(term recall)** — 용어집 항목이 정확히 전사되었는가.
- 비교군: (a) 베이스라인 (b) 레이어 1만 (c) 레이어 1+2 (d) 레이어 2만
- (d)가 (c)와 비슷하면 레이어 1은 버린다. 복잡도를 줄일 기회다.

## 8. 합격 기준

PoC 성공 = 아래 전부 충족:

1. Phase 0을 통과했고, 낭독 최대 글자 수가 실측되어 6.3에 반영되었다.
2. 용어 재현율이 베이스라인 대비 유의미하게 개선되었다 (목표: 20개 발화 기준 90% 이상).
3. 훅이 에이전트 세션에 체감 가능한 지연을 주지 않는다 (훅 실행 시간 < 50ms).
4. Relay를 강제 종료했다가 재시작해도 이벤트 유실 없이 이어진다.
5. **실제 연구 세션 하루를 돌렸을 때, 받은 내레이션 중 "이건 안 보내도 됐다"가 30% 이하이고, "이건 알았어야 했는데 못 받았다"가 0건이다.** ← 가장 중요한 기준.

## 9. 열린 질문 (구현자가 결정하거나 사용자에게 확인할 것)

- **Q1.** 사용자의 폰이 iOS인가 Android인가? Phase 0의 구체적 경로가 갈린다.
- **Q2.** Claude Code를 인터랙티브 TUI로 쓰는가, Agent SDK/헤드리스로 감싸서 쓰는가? 후자면 훅 대신 스트림을 직접 잡을 수 있어 통제력이 훨씬 좋다.
- **Q3.** 디바운스 시간과 발화 빈도 상한의 초기값. 실사용 하루 후 튜닝 필요.
- **Q4.** 요약 LLM을 어디로 호출할 것인가 (API 키 관리, 비용 상한).
