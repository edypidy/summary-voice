## 1. 문제 정의

연구자가 Claude Code 에이전트에게 연구 작업을 위임해 두고 자리를 비웠을 때, **현재 무엇이 진행되고 있는지를 폰에서 확인할 수 있어야 한다.** 지금은 터미널로 돌아가 코드를 직접 읽거나 에이전트에게 물어봐야만 파악이 된다.

부차적으로, 읽은 내용에 대해 되묻거나 지시할 수 있으면 좋다. **단, 받기가 쓸모 있다는 게 확인된 뒤다** (섹션 4). 받는 요약이 시시하면 답장할 일도 없다.

### 사용자 프로파일 (중요)
- 주 사용 언어: **한국어**. 단, 전문 용어는 영어를 그대로 섞어 씀 (code-switching).
- 도메인: 의료영상 AI 연구. 등장 용어 예시 — `LoRA-XS`, `Sinkhorn`, `Mutual EM Attention`, `STE hard selection`, `cross-attention`, `PEFT`, 그리고 레포 고유 식별자(`hierarchical_cross_attention.py` 등).
- 요약을 **읽으므로** 이 용어들은 원문 그대로 쓴다. 풀어 쓰면 오히려 알아보기 어렵다.

## 2. 범위

### PoC에 포함
- Claude Code 세션에서 이벤트 수집
- 이벤트 → 짧은 한국어 텍스트 요약

### PoC에서 제외

  Phase 0에서 실측해 탈락시켰다 (`docs/phase0-result.md`)

- 실시간(토큰 단위) 스트리밍 요약 — 마일스톤 단위로 충분
- 멀티 호스트, 인증, 다중 사용자
- 자체 모바일 앱

## 3. 아키텍처

```
[Host: 연구 머신]
  Claude Code Agent 1 ─┐
  Claude Code Agent 2 ─┼─(트랜스크립트 JSONL)─→ events.jsonl (append-only)
  ...                  ┘                              │
                                                      ▼
                                          Relay Daemon (별도 프로세스)
                                          - 디바운스 / 살리언스 판정
                                          - state.json 갱신
                                          - 요약 LLM 호출
                                                      │
                                                      ▼
                                            Telegram 봇 → 채팅 1개
                                                      │
[Device: 폰]                                          ▼
                                            알림으로 읽는다
```

### 핵심 설계 원칙 (위반 금지)

1. **관측과 제어는 별개 경로다.** Claude Code 세션은 서버가 아니므로 쿼리할 수 없다. PoC는 읽기만 구현한다.
2. **캡처는 논블로킹이어야 한다.** 캡처 안에서 LLM 호출·네트워크 I/O를 하면 연구 세션 자체가 느려진다. **JSON 한 줄을 쓰고 끝낸다.** 훅 경로를 쓸 경우 **항상 exit 0** (2는 블로킹 의미).
3. **Relay는 stateless여야 한다.** 모든 상태는 디스크에 있다. Relay가 죽었다 살아나도 events.jsonl부터 재구성 가능해야 한다.
4. **Relay는 Claude Code 에이전트가 아니라 단순 API 호출이다.** 요약기에 툴이나 파일시스템 접근 권한을 주지 않는다. 프로젝트마다 상주 에이전트를 띄우면 토큰 비용이 폭발한다.
5. **요약은 알림 한 개 분량을 넘지 않는다.** 섹션 6.3의 제약을 반드시 지킬 것.

## 5. 이벤트 수집

### 5.1 훅 설정

Claude Code Hooks를 사용한다. **구현 전에 반드시 최신 문서로 스키마를 확인할 것** — 훅 스펙은 자주 바뀐다.
- https://code.claude.com/docs/en/hooks
- Agent SDK로 감쌀 경우: https://platform.claude.com/docs/en/agent-sdk/hooks

사용할 이벤트:

| 이벤트 | 용도 | 비고 |
|---|---|---|
| `Stop` | **주 트리거.** 턴/작업 종료 = 마일스톤 | `session_id`, `transcript_path`, `cwd` 등을 전달받음. `transcript_path`가 요약 소스로 가장 유용 |
| `SubagentStop` | 서브에이전트 단위 완료 | 매처로 에이전트 타입 구분 가능 |
| `PostToolUse` | 보조 신호(어떤 파일/명령을 건드렸는지) | **관찰 전용.** 실행을 되돌리지 못함. 노이즈가 많으므로 필터 필수 |

주의사항:
- **매처는 대소문자를 구분한다.** `bash`는 `Bash`에 매칭되지 않는다.
- 훅 종류는 command / http / prompt 등이 있다. PoC는 **command 훅**을 쓴다 (디버깅이 쉽다).
- `exit 2`는 블로킹 의미를 가진다. 우리 훅은 **항상 exit 0** 해야 한다. 실수로 2를 반환하면 에이전트 동작에 개입하게 된다.
- 훅 등록 확인은 `/hooks`로, 테스트는 샘플 JSON을 stdin으로 파이프해서 종료 코드를 확인한다.

### 5.2 훅 스크립트 요구사항

```
stdin JSON 읽기
→ {ts, project, session_id, agent_id, event_type, payload} 로 정규화
→ <queue_dir>/<uuid>.json 으로 원자적 쓰기 (임시파일 write 후 rename)
→ exit 0
```

- 실행 시간 목표: **50ms 미만**. 네트워크 호출 금지.
- 어떤 예외가 나도 exit 0. 관측 레이어가 연구를 망가뜨리면 안 된다.
- `agent_id`를 반드시 넣을 것. 여러 에이전트가 동시에 돌 때 내레이션에서 구분해야 한다.

### 5.3 저장소 레이아웃

```
<project>/.assistant/
  queue/            # 훅이 쓰는 곳, Relay가 소비 후 삭제
  events.jsonl      # append-only, 원본 진실
  state.json        # events에서 파생된 현재 상태 (언제든 재생성 가능)
  narrations.jsonl  # 발송 이력 (중복 방지 + 평가용)
```

`state.json` 스키마:
```json
{
  "goal": "현재 진행 중인 상위 목표 (사람이 이해하는 단위)",
  "in_progress": ["..."],
  "recently_done": ["..."],
  "blockers": ["..."],
  "last_narration_ts": "...",
  "last_event_offset": 0
}
```
`last_event_offset`으로 Relay 재시작 시 이어받는다.

## 6. Relay Daemon

### 6.1 루프

```
큐 폴링 (또는 파일시스템 watch)
→ 디바운스: 마지막 이벤트 후 N초 정적일 때만 발화 (기본 N=30, 설정 가능)
→ 살리언스 판정 (6.2)
→ 발화할 가치가 있으면: state.json + 신규 이벤트 델타 → LLM → 요약
→ state.json 갱신, narrations.jsonl 기록, Telegram 전송
```

- 요약 모델: **Haiku 급**. 전체 트랜스크립트를 매번 넣지 말 것 — append-only라 금방 커진다. **state.json + 델타**만 넣는다.
- 프로젝트당 독립 워커. 프로젝트 간 상태를 섞지 않는다.

### 6.2 살리언스 — 이 PoC의 지적 핵심

가장 어려운 부분이자 결과물의 질을 좌우하는 부분이다. 목표는 **스팸도 아니고 중요한 걸 놓치지도 않는** 케이던스.

발화해야 하는 것:
- 마일스톤 완료 ("Sinkhorn OT 루프 구현 끝")
- 막힘/실패 (loss NaN, 테스트 실패, 반복되는 에러)
- 사람의 결정이 필요한 지점
- 방향 전환

발화하면 안 되는 것:
- 개별 파일 읽기/쓰기, `ls`, `grep`
- 진행 중인 중간 상태
- 직전 요약과 실질적으로 같은 내용

구현: 규칙 기반 1차 필터(이벤트 타입/툴 이름) → LLM 2차 판정(발화 여부를 boolean으로 먼저 물어보고, true일 때만 요약 생성). 2단계로 나누면 비용이 크게 준다.

### 6.3 요약 제약 (하드 제약)

**개정됨.** 이전 판의 제약 - 3문장 이하, 200자, "코드·경로·긴 식별자 금지",
"숫자 최소화" - 은 전부 **낭독 때문에** 있던 것이다. 폰으로 읽는다면 근거가 없다.

- **한국어**, `config.yaml`의 `max_chars` 이하 (기본 600자)
- **식별자·경로·줄 번호는 원문 그대로 쓴다.** `train.py:142`, `LoRA-XS`, `Sinkhorn`.
  풀어 쓰지 말 것 - 사용자는 이 용어로 사고하고, 터미널로 돌아갈 때 그대로 검색한다.
  ~~`hierarchical_cross_attention.py` → "크로스 어텐션 모듈"~~ 은 폐기됐다
- **숫자를 넣는다.** loss 값, 에폭, 소요 시간. 읽는 사람이 판단하는 데 쓴다
- 첫 줄이 결론이다. 알림 미리보기에서 잘려도 첫 줄만으로 무슨 일인지 알아야 한다
- 에이전트가 여럿이면 주어를 명시 ("2번 에이전트가...")
- 마크다운 문법을 쓰지 않는다 (6.4 참조)

**폰 알림에서 훑어보기 좋은가**가 기준이다. 정확한 식별자 하나가 매끄러운 문장보다 낫다.

### 6.4 Telegram

- **봇 1개 + 채팅 1개.** 프로젝트가 여럿이면 요약 첫머리에 프로젝트명을 넣어 구분한다.
- `sendMessage` 하나면 충분하다.
- **`parse_mode`를 절대 켜지 말 것.** 요약에는 언더스코어가 든 식별자가 그대로
  들어가는데(6.3), 마크다운 파싱을 켜면 그중 하나에 400이 나서 알림을 통째로 잃는다.
  키를 **아예 빼야** 한다 - `"parse_mode": None`으로 두면 JSON에 `null`이 실려
  나가고 텔레그램이 `400 unsupported parse_mode`로 거절한다. 실제로 겪은 버그다.

## 7. 전문 용어 처리 — 삭제됨

이 섹션은 용어집 자동 생성과 2중 레이어 STT 교정, 용어 재현율 평가를 다뤘다.
**전부 음성 입력을 위한 것이었고, 음성이 범위에서 빠지면서 함께 빠졌다.**

요약을 **읽으므로** 전문 용어는 아무 처리 없이 원문 그대로 쓰면 된다 (6.3).
이 프로젝트의 최대 기술 리스크였던 한국어-영어 code-switching 인식 문제는
음성 입력이 없어지면서 **문제 자체가 사라졌다.**

구현했던 코드(용어집 추출기, STT 교정, term recall 평가, 발화 20개)는
커밋 `5c58d8d` 에 있다. 되살리는 법은 `docs/phase0-result.md`.

## 8. 합격 기준

PoC 성공 = 아래 전부 충족:

1. ~~Phase 0 통과 및 낭독 글자 수 실측~~ → **완료.** 음성 탈락, 텍스트 채택 (`docs/phase0-result.md`)
2. ~~용어 재현율 90% 이상~~ → **삭제.** 음성 입력이 없으므로 잴 것이 없다
3. 캡처가 에이전트 세션에 체감 가능한 지연을 주지 않는다 (< 50ms).
4. Relay를 강제 종료했다가 재시작해도 이벤트 유실 없이 이어진다.
5. **실제 연구 세션 하루를 돌렸을 때, 받은 요약 중 "이건 안 보내도 됐다"가 30% 이하이고, "이건 알았어야 했는데 못 받았다"가 0건이다.** ← 가장 중요한 기준.

5번만이 진짜 기준이다. 3·4번은 5번을 재려면 시스템이 하루를 버텨야 해서 있는 것이다.

| Q6 | 음성을 쓸 것인가 | **아니오** | 문서 전체. Phase 0 실측 결과 (`docs/phase0-result.md`) |
| Q7 | 양방향(지시 전달)을 지금 만들 것인가 | **아니오, 받기 먼저** | 섹션 4 Phase 2 |

Q2가 바뀌면 이 표와 `CLAUDE.md`의 결정 표를 **같이** 고칠 것.

### 남은 미확인 사항

- `max_chars` 600은 **잠정값**이다. 폰 알림에서 실제로 몇 줄이 편한지는 하루 써봐야 안다
- 디바운스 30초 / 시간당 12회도 하루 뒤 튜닝 대상 (Q3)
- 살리언스 판정이 실제로 쓸 만한지 - 이게 섹션 8의 5번이고, PoC의 진짜 질문이다
